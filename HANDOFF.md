## Live test, round 1 — the stale-report bug (found and fixed same day, 2026-07-30)
Within hours of pausing Stylist Report uploads, the user reported "SS is not updating" / "showing 0 under SS" in every tab. Debugged live via the user's own browser console (the `[history load]` diagnostics already in the code, plus a new temporary one added mid-session) rather than guessing:

- **Confirmed the underlying data was fine**: 25,779 of 33,134 history records had nonzero Signature S after the user's Sales-Accrual upload, most recent dated 2026-07-29 (the last day that file covered) — inside the app's week-to-date default window (2026-07-27 to 2026-07-30, today). So the "Stylist Report is now optional" fallback's data pipeline itself was never the problem.
- **Actual root cause**: the fallback logic added earlier this session only activated when `report` was `null` (`usingDefaultRange = !report && ...`) — but `report` is Supabase-persisted state that **never expires on its own**. It's simply whatever Stylist Report was last uploaded, however long ago, until something new overwrites it. Since the user's last real upload was still sitting there, every one of the 6 fallback-aware tabs kept treating it as "the current report" and never switched over to the historical data at all — even though that live-report object *never had a Signature S field to begin with* (the Stylist Report export has no item-level detail, so `parseStylistReport`/`rollup()` never populated it). Every other field on that stale report still had real-looking (if increasingly outdated) numbers, which is exactly why only SS looked broken and nothing else did.
- **Fix**: new `isReportStale(report)` (`App.js`, next to `getCurrentWeekRange`) — a report counts as usable only if it exists AND its own `endDateISO` is within `REPORT_STALE_AFTER_DAYS` (10) of today. All 5 tabs' `usingDefaultRange` checks changed from `!report` to `isReportStale(report)`, so once the last real upload ages past ~10 days, they automatically switch to the historical fallback instead of showing an ever-more-stale snapshot forever. The `section-hint` copy shown in that state was reworded from "No live weekly report on file" to "No current weekly report on file" since it's no longer strictly about the report's existence, just its freshness.
- **Why 10 days**: a real weekly report is only ever meant to represent about a week; 10 gives a few days' grace for a slightly late upload without waiting a full extra cycle. Easy to tune if it turns out wrong in practice — it's the one constant (`REPORT_STALE_AFTER_DAYS`) at the top of `isReportStale`.
- **Temporary diagnostic left in `App.js`'s history-load block** (safe to leave, same "cheap and inert" reasoning as the existing `[history load]` logs): logs how many history records have the `signatureS` field at all vs. how many are actually nonzero, plus a sample of the 5 most recent nonzero ones. Directly answered "is the data missing, zero, or just not being looked at" without needing SQL access. Worth keeping around for the next time something like this comes up, or removing once the live test settles down if the console noise becomes annoying.
- **Verified**: real `npm run build`, clean. Not re-verified with a live click-through (still no local Supabase credentials) — this was debugged entirely through the user's own browser console output relayed back into the session, which worked well as a pattern; worth reusing if another "X isn't updating" report comes in before there's a way to test locally with real data.

## What shipped this session — Signature S fix, SS rename, DL Managers view, Reviews Pin List (2026-07-30)
Four asks in one session: two feature requests (DL Managers view, Reviews Pin List), one real bug fix (Signature S), and a rename that piggybacked on the bug fix since both touched the same field.

- **Root cause found for "Signature S not updating"**: `getRangeTotals` and `buildWeeklySnapshots` (`src/App.js`) both fully skip a day's daily history record whenever that date is already covered by an uploaded weekly Stylist Report — this is the existing, correct dedup rule that stops the two sources double-counting sales/hours/etc. But `buildWeeklyRecord` (`src/parser.js`) never captured Signature S at all (the routine Stylist Report has no item-level detail, so it can't). ## What shipped this session — employee login system
User asked for real login (District Leaders see only their store group, Managers only their store, Owner sees everything) plus an admin-managed roster that can revoke access. This is genuinely new infrastructure — every prior "password gate" in this app (`GOALS_PASSWORD`, the Setup tab's joke banner) was a client-side flag that reset on reload, not real auth. Full design reasoning is in the plan file the session used: `curried-booping-stonebraker.md` (Claude Code plan mode), worth reading if picking this back up since it explains the tradeoffs, not just the "what."

**Scope decision the user explicitly made**: protect only the sensitive data (sales numbers, goals, reviews) with real server-side enforcement this round — not a full lockdown of every read/write in the app. Rationale: the Supabase anon key is already public (compiled into the site's JS bundle, like any React app) and nothing currently restricts what it can read/write; truly closing that off means rewriting how every single tab loads *and saves* data (homepage news, goal edits, review notes, etc.), which is a much bigger and riskier job than "add login" alone. So: homepage news/events, the employee start-date list, review notes/gold combs, and **all writes app-wide** still go through the original direct-to-Supabase anon-key path, unchanged. Only reads of `stylist_report`, `store_goals`, `store_managers`, `milestone_goals`, `reviews`, and the `daily_history_*`/`weekly_history_*` chunks (+ legacy singular forms) are now server-filtered.

**How it works**:
- Two new Supabase tables need to be created by the user (SQL below) — `employees` (id, employee_code unique, phone unique, name, role, store_codes text[], **pin_hash** nullable, active, created_at) and `sessions` (opaque token, employee_id, created_at). Both need RLS enabled with **no policies** — that alone locks the public anon key out of them entirely; only a new Supabase **service-role key** (server-only, `SUPABASE_SERVICE_ROLE_KEY` in Vercel, never `REACT_APP_`-prefixed) can touch them. This is the same trick that let this round skip a full data-access rewrite: the existing `weekly_report` table's RLS/anon-key setup is untouched, but the *new* server-enforced endpoint reads it with the service-role key instead of the client reading it directly.
- **Login is a global PIN with no username at all** — this was a deliberate mid-session redesign away from phone+password. "Create a Login" (two-step wizard in `LoginScreen`, `src/App.js`) still checks employee code + phone against the roster the owner uploaded (`api/auth.js`'s `checkEligible` then `signup` actions), but once a PIN is set, "Sign In" is just the PIN — nothing else. **Consequence**: since there's no username to look an account up by, the PIN itself has to double as the identifier. `findEmployeeByPin` (`src/serverAuth.js`) finds the account by bcrypt-comparing the entered PIN against *every* active, registered employee's hash in turn (a hash can't be looked up directly) — used both by login and by signup (to reject a PIN someone else already has, since two people can't share one). This is deliberately O(n) in employee count and uses a lower bcrypt cost (8, not the usual 10) so that scan stays fast as the roster grows — fine at this franchise's scale, would need rethinking if the roster ever reached the thousands. PINs are validated as 5+ letters/numbers (`PIN_PATTERN` in both `LoginScreen` and `api/auth.js`).
- `api/auth.js` (checkEligible/signup/login/logout), `api/roster.js` (owner-only: list/upload/resetPin), `api/scoped-data.js` (the filtering endpoint — role `owner` gets everything unfiltered, everyone else gets their `store_codes` intersected against the payload). Sessions are opaque random tokens in the `sessions` table, not JWTs — every request re-reads the employee's *current* row fresh, so revoking someone (or changing their role/stores) takes effect on their very next request, not just their next login.
- **Setup > Employee Access** (new sub-tab, owner-only since the whole Setup tab is now hidden from non-owners) uploads the roster: one Excel/CSV with columns `Employee Name | Employee Code | Phone Number | Role | Store Codes` (Role: Owner/District Leader/Manager/Employee; Store Codes: comma/space-separated, only meaningful for DL and Manager rows). **Every upload replaces the full current list** — anyone whose employee code isn't in the new file gets `active = false`, which is what actually implements "remove someone from the list, they lose access." A "Reset PIN" button per row clears `pin_hash` so someone locked out (or who forgot their PIN — there's no self-service recovery) can create a new one.

Once logged in, the sensitive keys load via `loadScoped`/`loadScopedByPrefix` (`src/auth.js`) instead of `loadData`/`loadDataByPrefix` (`src/db.js`) — same `{data, source, error}` shape, so no call-site logic had to change beyond swapping which function is called. `TABS` hides `'Setup'` for non-owners. ## Post-launch bug — reports appeared to vanish (found and fixed same session)
Right after going live, the user reported stylist_report/history/goals data disappearing on every refresh, with no error shown. Root-caused via the deployed bundle + the user's own browser DevTools (Network/Console) rather than guessing — worth reading if a similar "data disappeared" report ever comes back, since the debugging path (pull the public anon key straight out of the deployed JS bundle to query Supabase directly and confirm the data still existed server-side) is a reusable technique for this kind of "is it a save bug or a read bug" question.

- **Actual cause**: this app already mirrors a lot of data into `localStorage` as a backup (`db.js`'s `saveData` — historical daily/weekly chunks, and especially `homepage_news`, which can carry base64-inlined images/PDFs up to 8MB each). On this user's browser that mirror had grown close to the browser's per-origin storage quota. `setSession()` (`src/auth.js`) writes the login session to `localStorage` too — a tiny write, but with zero headroom left it threw `QuotaExceededError`, which the original code caught and silently ignored. Meanwhile `loadScoped`/`loadScopedByPrefix` were re-reading the token via `getSession()` (i.e. re-reading `localStorage`) on every single fetch instead of trusting the token already held in React state — so with the session never actually persisted, every scoped fetch quietly saw "not logged in" and returned nothing, even within the same already-authenticated page view, no error surfaced anywhere.
- **Fix** (commit after the login-system launch commit): `loadScoped(key, token)`/`loadScopedByPrefix(prefix, token)` now take the token explicitly from `currentUser.token` (App.js) instead of re-reading `localStorage` — matches how `rosterList`/`rosterUpload`/`rosterResetPin` already worked. `setSession()` now returns whether the write actually succeeded; `LoginScreen`'s `onLoggedIn` passes that through to a new `handleLoggedIn` in `App.js`, which shows a toast ("you'll need to sign in again next time") when it didn't, instead of failing silently.
- **Not fixed / still true**: if a browser's localStorage is genuinely full, that browser still won't remember a login across a refresh (harmless now — just means signing in again next visit — but no longer causes data loss). The underlying cause (base64 images/PDFs from Homepage News accumulating in localStorage, per the existing "Known limitations" note further down) is unchanged; worth real attention if this keeps coming up for the user's own browser or anyone else's.

Shows the full Google Apps Script source (with the real webhook URL auto-filled via `window.location.origin`, but `SHARED_SECRET` always shown as a placeholder — **the real secret is never embedded in the deployed bundle**, since the Setup tab has no password gate and the bundle is public).
